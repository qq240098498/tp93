# tp93 检查规则与命中清单工作台

一个本地小工具：把团队约定要检查的写法整理成规则，把需要检查的文件内容收进来，点一下扫一遍，命中的地方会记到具体的文件与行上。规则不再是建出来就直接生效，而是走「起草 → 待复核 → 启用 → 停用」这条链：写完先自己复核，启用前系统再把一遍关，启用之后才参与扫描；停用之后不再参与，但历史上扫出来的命中全部留底，并看得出当时是哪一版规则在管事。每一次状态变化、每一次改版都记录在案。

数据全部存在本机的数据文件里，不连数据库，也不调用任何外部服务。

## 技术栈

- 后端：Node.js（>=18）与 Express，前后端同一个进程
- 前端：原生 HTML、CSS 与 JavaScript，页面文件由后端静态目录直接提供，没有构建步骤
- 存储：本地 JSON 文件 `data/db.json`

## 启动方式

```bash
npm install
npm start
```

启动后打开页面地址：<http://localhost:5093>

端口固定为 `5093`，如需临时改动可在启动前设置环境变量 `PORT`。

## 页面怎么用

1. 先在右上角填上**当前操作者**：规则的新建、改版、每一次状态流转以及扫描都要署名，没填会被拦下；名字记在本机浏览器里
2. 规则区列出编码、名称、级别、状态（带颜色标签）、版本、适用文件类型与匹配写法，可以按级别、状态、适用文件类型筛选，也能按编码、名称或匹配写法搜索
3. 新建规则一律先进**草稿**，起草阶段匹配写法可以先空着；草稿可编辑、可删除。写完点「提交复核」进入**待复核**，待复核中不能改正文，复核不通过可「退回起草」
4. 待复核或停用中的规则点「启用」，系统会逐项把关（见下），有一项不过都不会启用，并把卡在哪些项上一条条列出来
5. 启用中的规则只能「停用」，不能改正文、不能删除；停用之后可「编辑改版」，正文一改就升一版（只改说明不升版），再走启用才重新参与扫描
6. 每条规则行上有「记录」，点开是这条规则从登记至今的时间线：每一次是从什么状态到什么状态、什么时候、由谁做的、有没有写说明（没写会如实标「未写说明」），改版单独标出升到第几版
7. 文件区列出收录进来的文件路径、类型、行数与更新时间，点看内容可以把整份内容展开在下面；点编辑会把路径、内容与备注回填到表单，支持收录新文件与移出清单
8. 命中清单区顶部可以选定只看某一条规则、某一个文件或者某一个级别，点按规则扫一遍，页面上给出这一轮参与比对的规则条数、范围里的文件个数、一共命中多少条，并按级别、按规则（含管事版本）、按文件分别汇总
9. 下面的「历史扫描」列出每一轮是谁扫的、范围多大、命中多少条；点「看这一轮」可以回看当时的完整命中，每条命中都带着**当时管事的规则版本**。最近保留 200 轮
10. 任何一步不成立时，页面顶部给出说明，并尽量把问题标到对应的输入项上

## 状态流转

```
新建 ─→ 草稿 ─提交复核→ 待复核 ─启用→ 启用 ─停用→ 停用
              ↑─退回起草──┘                ↑─启用──┘
                                           （停用中可改版，改版升版本）
```

- 只有**启用**状态的规则参与扫描；草稿、待复核、停用都不参与
- 状态只能按线上的箭头走，越级操作（例如草稿直接启用）会被拒绝并写明现在能做什么
- 每次流转都要选择动作、署名，可附一段说明；无论写不写说明都会留一条记录
- 停用规则改版会升版本号（第 1 版、第 2 版……）；重新启用后，新扫描按新版本记，旧扫描里的命中仍标着旧版本

### 启用前的把关

点「启用」时下面四项会逐项检查，全部通过才放行；不过几项就列几项：

1. **匹配写法没写**（或空白）——不允许启用
2. **适用文件类型没选**（或值不在清单里）——不允许启用
3. **编码与清单里已有的规则撞上**（编码重复，不区分大小写）——不允许启用
4. **同类写法已经有另一条启用规则在管**——匹配写法完全相同，且适用文件类型范围有重叠（两边任一是「全部」或类型相同）就算撞；类型互不相交的可以并存

此外规则编码格式不对、超长、名称为空、级别不合法等，在保存时就会当场指出。

## 比对口径

- 只有状态为启用的规则参与比对，停用、草稿、待复核的规则不会产生命中；如果指定了一条非启用的规则，页面上会写明这一轮它没有参与
- 适用文件类型写成全部的规则管所有文件，写成某一种类型的只比对该类型的文件，类型按路径后缀判断（支持 js、sh、md、yml）
- 一条规则命中与否看文件里有没有出现它登记的匹配写法，区分大小写，命中的是包含这个写法的整行
- 命中按规则编码、文件路径、行号排序，同一行同时踩到多条规则时逐条各记一条
- 每条命中都记下当时规则的版本号与规则名称、级别、写法快照；规则后来改版甚至删除，旧扫描里仍看得出当时是哪一版

## 登记口径

- 规则编码写成大写字母加短横线加数字，例如 `CODE-001`，最长 20 个字符，且不能重复
- 级别只有三种：提示、警告、错误
- 状态有四种：草稿、待复核、启用、停用；只能通过流转动作改变，不能在编辑表单里直接选
- 匹配写法最长 60 个字符；起草阶段允许为空，启用时必须已填写
- 操作者名称最长 40 个字符；流转与扫描说明最长 200 个字符
- 文件路径最长 120 个字符，只用字母数字、点、下划线、短横线与斜线，后缀必须是收录范围内的几种，且不能重复
- 文件内容不能为空，最长 4000 个字符

## 数据存储

所有数据写在 `data/db.json`，结构为 `{ "rules": [...], "files": [...], "ruleHistory": [...], "scans": [...] }`：

- `rules`：规则正文，含状态、当前版本号 `version`、最近一次启用时的版本 `enabledVersion`、创建者与最近更新者
- `ruleHistory`：逐条记录每次状态流转（`kind: "transition"`）与停用中的改版（`kind: "revision"`），含动作、起止状态、版本、时间、操作者、说明与当时的规则内容快照
- `scans`：每一轮扫描的完整留底，命中里带规则版本；最近保留 200 轮

落盘时先把内容写进同名临时文件，再用改名的方式替换正式文件，写入过程中断也不会把数据文件写坏；文件缺失或内容损坏时会自动回落到初始数据。旧版本（只有启用/停用两态、没有版本与记录的数据文件）读入时会自动升级：按当前状态给每条规则补一条建账记录，停用规则再补一条停用记录。

## 接口一览

| 方法   | 路径              | 说明                                             |
| ------ | ----------------- | ------------------------------------------------ |
| GET    | /api/health       | 服务状态检查                                     |
| GET    | /api/rules        | 规则清单，支持按级别、状态、适用文件类型筛选与关键词搜索；每条带当前状态可做的动作 |
| POST   | /api/rules        | 新建规则（一律进草稿，需要 operator）            |
| GET    | /api/rules/:id    | 查看单条规则                                     |
| PATCH  | /api/rules/:id    | 修改规则（仅草稿、停用中可改；停用中改正文升版，需要 operator） |
| DELETE | /api/rules/:id    | 删除规则（仅草稿、待复核中可删）                 |
| GET    | /api/rules/:id/history | 一条规则的完整流转与改版记录                 |
| POST   | /api/rules/:id/transitions | 状态流转（提交复核/退回起草/启用/停用，需要 operator 与可选 reason） |
| GET    | /api/files        | 文件清单，支持按类型筛选与关键词搜索             |
| POST   | /api/files        | 收录文件                                         |
| GET    | /api/files/:id    | 查看单个文件（含完整内容）                       |
| PATCH  | /api/files/:id    | 修改文件                                         |
| DELETE | /api/files/:id    | 把文件移出清单                                   |
| POST   | /api/scan         | 按启用的规则扫一遍，落盘并返回命中清单与汇总（需要 operator） |
| GET    | /api/scans        | 历史扫描概要清单                                 |
| GET    | /api/scans/:id    | 某一轮历史扫描的完整命中（含当时的规则版本）     |

接口出错时统一返回 `{ "error": { "code": "...", "message": "...", "field": "...", "details": [...] } }`，其中 `field` 用于让页面把问题标到具体的输入项上；启用把关不过时 HTTP 状态为 422，`details` 里逐项给出卡点（错误码、说明、对应输入项）。
